Governance Layer = Unity Catalog

1. Metadata Governance

   - Catalog & Schema
     → Organizes data assets into a logical hierarchy for discovery and management.
     Definition:
     Catalog = Top-level container for data assets.
     Schema = Logical grouping of tables, views, and volumes within a catalog.

   - Classification & Tagging
     → Identifies and labels data (PII, Confidential, Restricted) for governance and compliance.
     Definition:
     Metadata labels attached to tables/columns to indicate sensitivity, ownership, business domain, or regulatory requirements.

2. Data Privacy & Protection

   - Data Minimization
     → Retains only the data required for business purposes and compliance.
     Definition:
     Collect, process, and store only the minimum data necessary.

   - Hashing, Tokenization, Encryption
     → Protects sensitive data from unauthorized access and exposure.

     Definition:
     Hashing     = One-way conversion of data into a fixed-length value (MD5, SHA-256, SHA-512).
	%sql
	-- MD5
	SELECT md5('john.doe@email.com') MD5 union all
	-- SHA-256
	SELECT sha2('john.doe@email.com', 256) SHA256 union all
	-- SHA-512
	SELECT sha2('john.doe@email.com', 512) SHA512;

     Tokenization = Replaces sensitive values with surrogate tokens.
		from pyspark.sql.functions import expr
		df = df.withColumn("customer_token",expr("uuid()"))

     Encryption   = Converts data into ciphertext that can be decrypted using a key.

   - Suppression, Generalization, Binning, Rounding, Truncation
     → Anonymizes or masks sensitive information while preserving analytical value.

     Definition:

Suppression     -> Email: mukesh@gmail.com  → NULL / Hidden
Generalization 	-> Age: 29                  → 20-30 years
Binning         -> Salary: 72,000          → 50K-100K bucket
Rounding        -> Salary: 72,456.78       → 72,500
Truncation      -> PAN: ABCDE1234F         → ABC****34F

3. Access Governance

- RBAC → Users, Groups, Service Principals
  → Grants permissions based on roles and responsibilities.

  Definition:
  Access is controlled through predefined roles and privileges.

  Examples:

  -- Grant access to a User
  GRANT SELECT  ON TABLE sales.customers  TO `mukesh@company.com`;

  -- Grant access to a Group (Recommended)
  GRANT SELECT ON TABLE sales.customers  TO analysts;

  -- Grant access to a Service Principal
  GRANT SELECT  ON TABLE sales.customers  TO `etl-sp`;

  -- Catalog Level
  GRANT USE CATALOG  ON CATALOG sales  TO analysts;

  -- Schema Level
  GRANT USE SCHEMA  ON SCHEMA sales.customer  TO analysts;

  -- Table Level
  GRANT SELECT, MODIFY  ON TABLE sales.customer.customers  TO analysts;

  -- View Existing Grants
  SHOW GRANTS ON TABLE sales.customer.customers;

  -- Check Current User
  SELECT current_user();

  -- List Groups (workspace-level)
  SHOW GROUPS;


- ABAC → Region, Department, Project attributes
  → Grants access dynamically based on user and data attributes.

  Definition:
  Access decisions are based on attributes associated with users, data, and environment.

  Examples:

  -- Region-based access
  CREATE OR REPLACE VIEW sales.customers_secure AS
  SELECT *  FROM sales.customers  WHERE region =
        CASE
            WHEN current_user() = 'mukesh@company.com' THEN 'India'
            WHEN current_user() = 'john@company.com' THEN 'US'
        END;

  -- Department-based access
  CREATE OR REPLACE VIEW finance.employee_secure AS
  SELECT *  FROM finance.employee  WHERE department =
        CASE
            WHEN is_account_group_member('finance_team')
                 THEN 'Finance'
            WHEN is_account_group_member('hr_team')
                 THEN 'HR'
        END;

  -- Project-based access
  CREATE OR REPLACE VIEW projects.secure_projects AS
  SELECT *  FROM projects.project_data  WHERE project_name IN (
      SELECT project_name      FROM governance.user_project_mapping      WHERE user_email = current_user()  );

  -- Check Current User
  SELECT current_user();

  -- Check Group Membership
  SELECT is_account_group_member('finance_team');

   - Row-Level Security
     → Restricts which rows a user can view.
     Definition:
     Users see only records matching authorized conditions (e.g., Region = India).

  -- Row-Level Security
  CREATE ROW FILTER region_filter  AS (region = current_user_region());
  ALTER TABLE sales.customers  SET ROW FILTER region_filter;

   - Column-Level Security
     → Restricts access to sensitive columns.
     Definition:
     Sensitive columns are hidden or masked based on permissions.
  -- Column-Level Security (Masking)
  CREATE OR REPLACE VIEW employee_secure AS
  SELECT      emp_id,      name,
      CASE
          WHEN is_account_group_member('hr_team')
          THEN salary
          ELSE NULL
      END AS salary
  FROM employee;


   - Dynamic Views
     → Presents different data to different users from the same underlying table.
     Definition:
     Views apply filtering and masking logic dynamically at query time.

4. Compliance

   - Data Lineage
     → Tracks data flow from source to consumption for impact analysis and traceability.
     Definition:
     End-to-end visibility of data movement across Bronze, Silver, Gold, and BI layers.

   - Audit Logs
     → Records who accessed or modified data and when.
     Definition:
     Maintains a history of user activities, permission changes, and data operations.

   - Access Monitoring
     → Continuously monitors permissions and data access for security and compliance.
     Definition:
     Tracks access patterns, detects anomalies, and supports regulatory compliance.

30-SECOND INTERVIEW ANSWER

Metastore is the top-level governance layer. Storage Credential defines how Databricks authenticates to cloud storage, and External Location defines which storage path can be accessed. Data is organized as Catalog → Schema → Table. Unity Catalog stores metadata, permissions, lineage, and governance information, while the actual Delta/Parquet files physically reside in ADLS, S3, or GCS.

What are the differences between Hive Metastore and Unity Catalog? Why would you choose Unity Catalog? 

Hive Metastore vs Unity Catalog

1. Governance Scope

Hive Metastore
   -> Governance is limited to a single workspace
   -> Security and permissions managed separately in each workspace
   -> Difficult to maintain consistent policies across environments
   -> More administrative overhead as the number of workspaces grows

Unity Catalog
   -> Centralized account-level governance
   -> Single governance layer across multiple workspaces
   -> Consistent security model across Dev, Test, and Production
   -> Easier compliance and policy enforcement

------------------------------------------------------------

2. Hierarchy

Hive Metastore
   -> Schema → Table

Example:
   sales_db.customer

Unity Catalog
   -> Catalog → Schema → Table

Example:
   sales_catalog.silver.customer

Benefits:
   -> Better organization of enterprise data
   -> Logical separation of business domains
   -> Easier data ownership management

------------------------------------------------------------

3. Access Control

Hive Metastore
   -> Basic permissions
   -> Mainly table-level access control
   -> Limited granularity

Unity Catalog
   -> Fine-grained permissions
   -> Control access at:
      Catalog
      Schema
      Table
      View
      Function
      Volume
      Model

Example:
   Analyst can read tables but cannot modify them.
   Data Engineer can create tables but cannot manage permissions.

------------------------------------------------------------

4. RBAC (Role-Based Access Control)

Hive Metastore
   -> Roles managed at workspace level
   -> Difficult to maintain across many workspaces

Unity Catalog
   -> Centralized role management
   -> Supports:
      Users
      Groups
      Service Principals

Example:
   Data Engineers Group
      -> Read/Write Silver
      -> Read Gold

   Analysts Group
      -> Read Gold only

------------------------------------------------------------

5. ABAC (Attribute-Based Access Control)

Hive Metastore
   -> No native support
   -> Requires custom implementation

Unity Catalog
   -> Native support using tags and policies

Example:

Table Tag:
   classification = confidential

User Attribute:
   department = finance

Policy:
   Finance users can access confidential finance data.

Benefits:
   -> Dynamic access control
   -> Less manual permission management
   -> Scales better for large organizations

------------------------------------------------------------

Hive Metastore
   -> Create separate views

Unity Catalog
   -> Native Row Filters

Example:

APAC 3000

Benefits:
   -> One table

CREATE OR REPLACE FUNCTION region_filter(region STRING)
RETURN
    CASE
        WHEN is_account_group_member('finance_team')
             THEN TRUE
        WHEN current_user() = 'john@company.com'
             AND region = 'US'
             THEN TRUE
        WHEN current_user() = 'alice@company.com'
             AND region = 'EU'
             THEN TRUE
        ELSE FALSE
    END;


ALTER TABLE sales
SET ROW FILTER region_filter ON (region);

Why We Chose Unity Catalog in Our Project

1. Multiple Databricks workspaces needed a single governance model.
2. Business required centralized security management.
3. Sensitive customer data required masking and row-level filtering.
4. Compliance team needed audit logs and lineage.
5. Data had to be shared securely with external consumers.
6. Manual permission management in Hive Metastore would not scale.
7. Unity Catalog enabled RBAC and ABAC from a single place.
8. Easier impact analysis using lineage.
9. Better dataset discovery for analysts and business users.

What are Delta Live Tables (DLT) Pipelines?

Delta Live Tables (DLT) is a Databricks framework used to build, manage, and monitor reliable data pipelines. It simplifies ETL/ELT development by allowing developers to define transformations declaratively while Databricks automatically handles orchestration, dependency management, monitoring, and optimization.

Instead of manually creating and scheduling jobs, developers define tables and transformations, and DLT manages the execution flow automatically.

--------------------------------------------------

Delta Live Tables (DLT)

1. Development & Pipeline Management Features
--------------------------------------------------
✓ Declarative pipeline development
✓ Automatic dependency management
✓ Automatic orchestration
✓ Pipeline graph visualization
✓ Lineage tracking
✓ Automatic recovery from failures
✓ Event logs and monitoring

Example:
Bronze → Silver → Gold

DLT automatically determines execution order.

--------------------------------------------------

2. Data Processing Features
--------------------------------------------------
✓ Streaming tables
✓ Materialized views
✓ Incremental processing
✓ Batch and streaming support
✓ Automatic checkpoint management

Example:
Only new files are processed instead of reprocessing all data.

--------------------------------------------------

3. Data Quality Features
--------------------------------------------------
✓ Expectations (data quality rules)
✓ Drop invalid records
✓ Fail pipeline on bad data
✓ Track quality metrics

Example:

@dp.expect("valid_age", "age >= 18")

--------------------------------------------------

4. CDC & Historical Data Features
--------------------------------------------------
✓ Change Data Capture (CDC)
✓ SCD Type 1 Support
✓ SCD Type 2 Support
✓ Automatic handling of Inserts, Updates, Deletes

Example:

dp.create_auto_cdc_flow(
    stored_as_scd_type="2"
)

--------------------------------------------------

5. Performance & Optimization Features
--------------------------------------------------
✓ Auto Optimize
✓ Auto Compaction
✓ Delta Lake optimizations
✓ Incremental execution

Benefits:
- Better performance
- Reduced manual tuning
- Lower operational effort

--------------------------------------------------

Advantages
--------------------------------------------------
✓ Less ETL code

✓ Automatic orchestration
✓ Data quality enforcement
✓ CDC support

Limitations / Disadvantages
--------------------------------------------------

A. Platform Limitations

Interview Answer

DLT provides five major capabilities:
1. Pipeline Management (orchestration, lineage, monitoring)
2. Data Processing (streaming, batch, incremental processing)
3. Data Quality (expectations and validations)
4. CDC & SCD Handling (CDC, SCD Type 1 and Type 2)
5. Performance Optimization (auto optimize and auto recovery)

Its main limitations are vendor lock-in, higher cost for continuous pipelines, less control compared to custom Spark jobs, and increased complexity when debugging advanced workloads.

What is Databricks Auto Loader?

Databricks Auto Loader is a cloud-native file ingestion tool that incrementally and efficiently processes new files arriving in cloud storage (AWS S3, Azure ADLS, GCS) and loads them into Delta tables using Structured Streaming.

It is the recommended approach for Bronze layer ingestion because it automatically discovers and processes only new files without repeatedly scanning the entire directory.

--------------------------------------------------

How Auto Loader Works

1. Monitors Cloud Storage
   ↓
2. Detects New Files
   ↓
3. Tracks Processed Files
   ↓
4. Reads Only New Files
   ↓
5. Loads Data into Delta Table
   ↓
6. Stores Metadata & Checkpoints

--------------------------------------------------

Key Features

1. Incremental File Processing
✓ Processes only new files
✓ Avoids reprocessing existing files

Example:
Day 1 → 100 files
Day 2 → 10 new files

Auto Loader processes only the 10 new files.

--------------------------------------------------

2. Schema Inference

Automatically detects schema from incoming files.

Example:

customer_id
customer_name
email

No need to manually define schema for simple use cases.

--------------------------------------------------

3. Schema Evolution

Automatically handles new columns.

Example:

Day 1:
id, name

Day 2:
id, name, country

Auto Loader can evolve the schema and add the new column.

--------------------------------------------------

4. Scalability

✓ Handles millions of files
✓ Better than manually listing directories
✓ Optimized for large-scale ingestion

--------------------------------------------------

5. Fault Tolerance

Uses checkpointing.

If the job fails:

File 1 ✅
File 2 ✅
File 3 ❌

After restart:

Resumes from File 3 instead of starting over.

--------------------------------------------------

6. Exactly-Once Processing

Each file is processed only once.

Benefits:
✓ No duplicates
✓ Reliable ingestion

--------------------------------------------------

7. Supports Multiple Formats

✓ CSV
✓ JSON
✓ Parquet
✓ Avro
✓ XML (with libraries)

--------------------------------------------------

Discovery Modes

1. Directory Listing Mode

Auto Loader scans storage periodically.

Example:

/landing/customer/

Checks for new files.

Simple but can become slower for very large directories.

--------------------------------------------------

2. File Notification Mode

Uses cloud notifications.

Azure:
Event Grid

AWS:
SQS

GCP:
Pub/Sub

Benefits:
✓ Faster
✓ More scalable
✓ Lower storage listing cost

--------------------------------------------------

Interview Answer

Databricks Auto Loader is a scalable file ingestion mechanism built on Structured Streaming that automatically detects and processes new files from cloud storage. It supports schema inference, schema evolution, checkpointing, fault tolerance, and exactly-once processing. Auto Loader is commonly used to ingest data into the Bronze layer of a Medallion Architecture because it efficiently processes only newly arrived files rather than scanning the entire source directory each time.

Why is Liquid Clustering generally not recommended for small tables?

Because the benefits of Liquid Clustering are often smaller than the overhead required to maintain it.

--------------------------------------------------

1. Small Tables Already Read Quickly

Example:

Customer Table = 100 MB

Query:

SELECT * 
FROM customer
WHERE customer_id = 100;

Spark can read 100 MB very quickly.

There is little performance gain from clustering.

--------------------------------------------------

2. Data Skipping Benefits Are Minimal

Liquid Clustering improves data skipping.

For a large table:

10 TB
↓
Read only 100 MB

Huge benefit.

For a small table:

100 MB
↓
Read only 20 MB

Very little improvement.

--------------------------------------------------

3. Additional Maintenance Overhead

Databricks must continuously:

✓ Monitor clustering keys
✓ Reorganize data
✓ Rewrite files

For small tables, the maintenance cost may exceed the performance benefit.

--------------------------------------------------

4. Small Tables Usually Fit in Memory

Example:

50 MB dimension table

Spark can often:

✓ Cache it
✓ Broadcast it

Example:

Broadcast Hash Join

No clustering needed because the entire table is already in memory.

--------------------------------------------------

5. Extra Compute Cost

Liquid Clustering requires background optimization activities.

For a table with only a few thousand rows:

Benefit ≈ 0
Cost > Benefit

--------------------------------------------------

When Liquid Clustering Makes Sense

✓ Large Delta tables
✓ Hundreds of GBs or TBs
✓ Frequently filtered columns
✓ High data growth rate
✓ Many concurrent queries

Examples:

sales_fact
transactions
clickstream
telemetry_data

--------------------------------------------------

When Not to Use Liquid Clustering

✗ Small lookup tables
✗ Small dimension tables
✗ Tables under a few GBs
✗ Rarely queried datasets

Examples:

country_codes
currency_lookup
department_master

--------------------------------------------------

Interview Answer

Liquid Clustering is generally not recommended for small tables because small tables are already fast to scan and often fit entirely in memory. The performance gains from improved data skipping are minimal, while the clustering maintenance introduces additional compute and storage overhead. Liquid Clustering provides the most value for large, frequently queried Delta tables where reducing I/O can significantly improve query performance.
