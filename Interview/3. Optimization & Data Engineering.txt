Explain Deletion Vectors. How are delete operations handled internally and when is storage reclaimed? 

DELETE operations in Delta Lake with Deletion Vectors are logical deletes. 
Delta does not immediately rewrite parquet files. 
Instead, it creates a bitmap-like deletion vector that records which rows are deleted 
and stores this information in the transaction log. 
Queries read both the data file and the deletion vector 
and automatically exclude deleted rows.

Physical storage is reclaimed later when OPTIMIZE rewrites the files 
and VACUUM removes obsolete files.

WHEN TO USE OPTIMIZE, ZORDER, AND LIQUID CLUSTERING
====================================================
OPTIMIZE is used to compact small files into larger files and improve scan performance.

ZORDER is used when queries frequently filter on specific columns,
allowing Delta Lake to collocate related data and improve data skipping.

Liquid Clustering is the newer adaptive data layout technique that
automatically organizes data based on clustering keys, 
reducing maintenance and providing better
flexibility than traditional partitioning and many
ZORDER use cases.

How have you implemented Delta Change Data Feed (CDF) for incremental processing? 

In my projects, I enabled Delta Change Data Feed on Bronze Delta tables and used it to build incremental
Bronze-to-Silver pipelines. Instead of reading the entire table on every run, I stored the last processed
Delta version and read only the changes using readChangeFeed=true and startingVersion. The CDF output
provided insert, update, and delete events along with commit metadata. I then used MERGE statements to apply
those changes to Silver tables, ensuring efficient and idempotent processing. This significantly reduced
runtime, compute costs, and data scanned compared to full table loads.
