the Driver first creates a Logical Plan.

Since collect() is an action, Spark creates one Job.

What is the difference between repartition() and coalesce()? When would you use each? 

REPARTITION() vs COALESCE()

repartition() performs a full shuffle and is used when increasing
or redistributing partitions for better parallelism, while
coalesce() minimizes data movement and is used mainly to reduce
partitions efficiently, especially before writing output files.

What are the common causes of Driver Out Of Memory (OOM) errors? 


Interview Answer
================

Common causes of Driver OOM are:
- collect() on large datasets -- transfers all records from executors to the driver, and if the data size exceeds the driver's available memory, the driver JVM crashes with OutOfMemoryError

- toPandas() on large datasets -- toPandas() moves all data from executors to the Driver. Because Pandas is single-node and stores all data in Driver memory, large datasets can exceed available memory and cause a Driver OutOfMemory (OOM) error.


- Large take() or show() operations.
- Broadcasting large tables.
- partitions causing metadata overload.
- small files Millions of 
- Large Python objects on Driver
- Very complex DAGs with many joins/unions.

Best practice:
Keep data distributed on Executors and avoid bringing large datasets back to the Driver.

One customer_id contains 40% of records in a 10 TB dataset and joins are extremely slow. How would you identify and resolve data skew? 

Data Skew Handling (customer_id = 40% of 10 TB data)

Problem Identification:
• Check Spark UI → Stages → Tasks.
  - Few tasks run much longer than others = skew.

• Analyze key distribution.
  - Find customer_id with unusually high record count.

• Check partition sizes.
  - One partition much larger than others indicates skew.

Impact:
• Most records go to a single executor during shuffle.
• One executor becomes a bottleneck while others remain idle.
• Join and aggregation operations become very slow.

Resolution:

1. Salting Technique
   - Add a random salt value to the skewed customer_id.
   - Distributes records across multiple partitions.
   - Most common solution for heavy skew.

2. Skew Join Optimization
   - Enable Adaptive Query Execution (AQE).
   - Spark automatically detects and splits skewed partitions.

3. Broadcast Join
   - If one table is small, broadcast it.
   - Eliminates expensive shuffle.

4. Repartition
   - Increase number of partitions.
   - Improves workload distribution.

5. Filter/Process Skewed Key Separately
   - Handle the heavy customer_id in a separate path.
   - Process remaining data normally and union results.

Interview Answer:
• Identified skew using Spark UI and key frequency analysis.
• Found one customer_id holding 40% of records.
• This forced most shuffle data to a single partition, slowing joins.
• Resolved using salting + AQE skew join optimization and broadcast join where applicable.
• Result: Balanced partitions, reduced shuffle bottlenecks, faster join performance.


I would first identify skew by checking customer_id distribution and analyzing Spark UI for long-running tasks, high shuffle reads, and skewed partitions. Since one customer_id contains 40% of a 10 TB dataset, Spark sends a large portion of data to a single partition during the join, creating a bottleneck. To resolve this, I would enable AQE skew join handling, apply salting to distribute the skewed key across multiple partitions, use a broadcast join if the lookup table is small, or process the hot key separately. These approaches improve parallelism, reduce shuffle bottlenecks, and prevent executor OOM issues.

You are processing 50 TB/day. A team proposes skipping the Silver layer and loading directly from Bronze to Gold. Would you approve this design? Explain the trade-offs. 

For a 50 TB/day enterprise workload
I would generally not approve removing the Silver layer. 
The Silver layer provides data cleansing, deduplication, schema enforcement, and reusable business transformations. 
Skipping it may reduce storage and latency, but it increases data quality risks, 
duplicates transformation logic across Gold tables, complicates troubleshooting, and makes reprocessing more expensive. 
I would only consider Bronze-to-Gold architecture for very simple or low-latency use cases. 
For large-scale production data platforms, the Bronze-Silver-Gold architecture remains the recommended design because it provides better scalability, governance, maintainability, and reliability.
